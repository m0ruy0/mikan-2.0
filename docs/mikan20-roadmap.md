# Mikan 2.0 — дорожная карта разработки

> Статус: проектирование и прототипирование. Этот документ не означает, что перечисленные функции уже реализованы.

Mikan 2.0 — независимый форк [Mikan](https://github.com/Miroshka000/mikan). Цель — сохранить рабочую основу панели и развивать дополнительные функции открыто, без блокировки базовых возможностей за сборами средств.

## Принципы

- **Безопасность и обратимость:** не менять рабочую `main` напрямую; разработки ведутся в отдельных ветках, изменения проходят CI и ревью.
- **Открытая базовая версия:** миграция панели, внешние источники подписок и административный Telegram-бот входят в бесплатную основную поставку.
- **Совместимость:** существующие VPS-ноды и текущий формат подписок продолжают работать, если функция специально не требует миграции.
- **Расширяемость без root-доступа:** аддоны не получают Docker socket, права хоста или секреты панели по умолчанию.
- **Прозрачность форка:** сохраняются уведомления об авторстве и GPL-3.0; в интерфейсе и документации явно указывается, что Mikan 2.0 — модифицированный форк.

## 1. Ноды на Pterodactyl

### Цель

Позволить запустить ноду на обычном игровом хостинге, где пользователь получает только сервер Pterodactyl и выделенные allocations, без SSH/root и без собственного Docker daemon.

### Техническая отправная точка

- `cmd/mikan-node` — отдельный Go-бинарник ноды.
- Нода запускает mihomo как библиотеку; сетевые listeners открываются самим процессом.
- Удалённая панель и нода соединяются по TLS через API-порт, заданный в ключе подключения.
- Текущий установщик для VPS опирается на Docker, host networking, постоянные каталоги и настройки хоста. Внутри Pterodactyl нельзя предполагать наличие этих привилегий.

### MVP

1. Подготовить отдельный standalone-бинарник `mikan-node` для Linux amd64 и arm64. Его распространение должно идти через проверяемые release assets с checksum; нельзя скачивать исполняемый файл по непроверенной плавающей ссылке.
2. Сделать Egg, который запускает бинарник от имени пользователя контейнера и хранит состояние в выделенном persistent directory.
3. В качестве переменной передавать ключ подключения; секрет не должен печататься в startup logs.
4. API-порт ключа обязан совпадать с портом, выделенным хостингом. Внешние inbound-порты TCP/UDP должны быть выделены и сопоставлены отдельно.
5. В панели добавить понятный режим «Pterodactyl» с проверкой allocations и сетевой доступности перед завершением настройки.
6. Проверить старт, остановку, перезапуск, восстановление после обновления, сбор статистики и переподключение к панели.

### Ограничения и проверки

- Один allocation для API не означает, что для клиентского VPN-трафика доступны все нужные TCP/UDP-порты.
- Провайдер может фильтровать UDP или не разрешать дополнительные allocations. В таком окружении нода должна показывать точную причину несовместимости, а не отмечаться как работающая.
- Режим MVP не должен требовать Docker socket, privileged container, host networking или изменения маршрутов хоста.
- WARP, TUN, каскады и функции, требующие доступа к сети хоста/специальных возможностей ядра, не заявляются совместимыми, пока это не проверено отдельно.
- Egg должен поддерживать graceful shutdown; файл состояния и счётчики должны переживать перезапуск контейнера.

**Критерий готовности:** нода успешно добавляется в тестовую Mikan 2.0 из Pterodactyl без root-доступа, принимает только выделенные ей порты, отображается как healthy, выдаёт рабочую тестовую подписку и корректно сохраняет счётчики после перезапуска.

## 2. Общая система аддонов и магазин

В исходном проекте marketplace сейчас ориентирован на платёжные адаптеры. Это не нужно ломать: платёжные адаптеры станут одной категорией общей системы.

### Категории

- несколько готовых Telegram-ботов: продажи/продление, поддержка, уведомления и администрирование;
- платёжные адаптеры;
- рефералы, промокоды и кампании;
- мониторинг и аналитика;
- интеграции с CRM, внешними API и сторонними панелями.

### Манифест аддона

Минимальная модель должна содержать:

- `id`, название, описание, версию и автора;
- совместимый диапазон версий панели и версию протокола;
- категорию, документацию и ссылку на исходный код;
- digest артефакта, подпись каталога и release channel;
- необходимые разрешения/scopes;
- список полей настройки с пометкой секретных значений;
- health check, состояние установки и план безопасного обновления/удаления.

### Безопасная модель запуска

- Исполняемый аддон запускается изолированно от процесса панели.
- Нельзя монтировать Docker socket, каталог данных панели, PostgreSQL или файл ключей.
- Аддон получает только собственный токен с ограниченными scopes.
- По умолчанию запрещены произвольные образы и неподписанные каталоги.
- Обновление сначала проверяет совместимость и digest; при ошибке старая версия остаётся доступной.
- Удаление аддона не удаляет пользовательские данные без отдельного подтверждения и политики хранения.

### Первый этап

1. Вынести общую модель каталога и capability/scopes.
2. Сохранить обратную совместимость текущих payment adapters.
3. Добавить категории, страницы описания, конфигурации и состояния аддонов.
4. После стабилизации API выпустить примеры одного бот-аддона и одного адаптера.

## 3. API для собственных ботов

В панели уже есть API-ключи. Следующий шаг — сделать безопасный API-контракт для внешних интеграций, а не выдавать сторонним ботам полный доступ администратора.

Нужны:

- scopes по операциям: чтение, клиенты, подписки, тарифы, устройства, ноды, уведомления;
- срок действия, отзыв ключа, журнал использования и ограничение частоты запросов;
- webhooks с подписью, временем события и защитой от повторного воспроизведения;
- стабильная версия API, OpenAPI-описание и примеры на Python;
- секреты оплаты и действия, перемещающие деньги, остаются доступны только через защищённую админ-сессию, если операция не делегирована явным образом.

## 4. Бесплатные возможности основной панели

### Перенос панели на другой сервер

- создание и проверка резервной копии;
- экспорт базы данных и данных панели, версии и схемы миграций;
- пошаговое восстановление на целевом сервере;
- повторная проверка нод и сертификатов;
- атомарное переключение с возможностью отката;
- режим dry-run и отчёт до внесения изменений.

Перенос не должен обещать перенос действующих IP-адресов или доступности старого сервера; внешние адреса/DNS пользователь переключает отдельно.

### Внешние подписки как источники нод

- добавление внешнего URL и проверка формата;
- периодическое обновление и отображение времени последней успешной загрузки;
- нормализация поддерживаемых протоколов/конфигураций;
- сохранение последней рабочей версии при временной ошибке источника;
- SSRF-защита: запрет loopback, link-local, приватных IP и cloud metadata адресов; безопасная обработка DNS, редиректов, портов и размера ответа;
- понятные правила конфликтов, дедупликации и обработки удалённых серверов.

### Административный Telegram-бот

- отдельный от клиентского бота режим/бот;
- allowlist Telegram ID администраторов и обязательное явное включение;
- команды для поиска клиентов, просмотра/продления подписок, состояния нод и основных показателей;
- подтверждение опасных действий и журнал аудита;
- никакой передачи токена бота, API-ключей или паролей в чат/логи;
- разрешения по ролям; по умолчанию бот работает в режиме чтения.

Все три возможности планируются как часть бесплатной основной версии.

## Definition of Done

Новая функция считается готовой, когда есть реализация, тесты/проверяемый сценарий, документация, обработка ошибок, меры безопасности и способ безопасного обновления/отката. Одного макета интерфейса или записи в roadmap недостаточно.
